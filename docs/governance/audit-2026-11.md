# Governance audit — November 2026

Branch `governance-audit`. Migration to apply to production **before deploying the code**:
**`supabase/migrations/20261226100000_governance_audit.sql`** (additive, idempotent; see
[migrations](../migrations.md)).

Trigger: Viewer-role users saw the **Build** menu. This audit checked every layer for every object
type (permission catalogue and role defaults, navigation and UI, page guards, server reads /
actions / services / REST / MCP, RLS, object-level grants, API keys and OAuth) and fixed what it
found. The docs (`lib/docs/content/governance.ts`, the generated roles table) are the spec; where
docs and defaults disagreed, least privilege won and the docs were updated.

## Root cause: why a Viewer saw Build

1. **The Viewer default held build permissions.** `seed_tenant_roles` and `lib/tenant-provisioning`
   gave Viewer `workflows.view`, `forms.view` and `data.view`. The side menu shows a group when any
   of its items is visible, so Workflows, Forms, Email templates (all `workflows.view` / `forms.view`)
   and Data made **Build** appear; Schedules and Business rules (`workflows.view`) and Organization /
   Team (`org.view`, `team.view_members`) filled **Operate** and **Govern**.
2. **`workflows.view` / `forms.view` were not "harmless reads".** They return full workflow
   definitions, integration reference pickers, form libraries and themes (ui-reads
   `automations.*` / `forms.*`, REST, MCP) — design data a read-only consumer shouldn't browse.
3. **Group placement ignored intent.** A read-only item (Data for a Viewer) still sat under a
   "Build" heading.

Fix: Viewer and Member lose `workflows.view` / `forms.view` (system roles only); the menu is built
per person (`resolveNavGroups`): read-only Data moves to **Operate**, the people directory to a new
**People** group, and Build / Govern only list areas the person can change.

## Behaviour changes users will notice

- **Viewer**: no Build / Govern / Settings in the menu; Data under Operate, Organization and Team
  under People. Workflow, form library, schedules, business rules, analytics pages and workspace
  settings tabs say *Not authorized*. Still: Home, own tasks, forms they are given (Forms menu),
  reports (own and shared, the People tab), data, profile and preferences.
- **Member**: same as Viewer plus creating / assigning tasks, editing rows, building their own
  reports, and **Operate › Queue** showing only the runs they are involved in (and every run of
  workflows explicitly shared with them). Saved reports on the tasks / runs sources need
  `tasks.view_all` / `workflows.view_runs` (they only ever saw their own tasks in the app).
- **Everyone with `tasks.complete` only**: can change only tasks they assigned, are on (assignee,
  collaborator, team, or as the assignee's manager) or whose parent they can reach.
- **Manager**: GitHub sync actions now open to them (they hold `sync.manage`, as REST always
  allowed). Reading an object's grants works for editors of that object.
- **Owner / Admin**: nothing removed.
- **API keys**: a user key follows its user's current roles; keys of removed / deleted users stop
  working (401). Tenant keys without a list are still full (legacy). Tenant keys need
  `workflows.view_runs` for run lists (they have no person to be "involved").

## Remaining risks and decisions for the owner

1. **SELECT on build tables is still membership-wide in RLS** (workflows, integrations, custom
   tables…). App surfaces gate reads by permission, but a member with the browser session token can
   read definitions straight through PostgREST. Gating SELECT would break embedded joins
   (task → workflow name, etc.); a follow-up could move those reads server-side and then restrict.
   `tenant_connectors` stays readable for the same reason (GitHub sync bookkeeping reads it on every
   save); its secrets are encrypted with `ENCRYPTION_KEY`.
2. **`tasks` RLS** is membership-wide for writes; the app now scopes every task mutation
   (`canReachTask`), the database does not (a row-level rule would need the reporting-line and team
   logic in SQL).
3. **`github_sync_queue` / `github_sync_asset_map`** stay member-writable (every builder's save
   records its change there through the session client).
4. **Member emails in pickers** (`governance.userOptions`, `tasks.redirectUsers`…) are visible to
   any member (Viewer included via `team.view_members`) — deliberate for assignment, but custom
   roles without `team.view_members` still get them.
5. **`settings.manage_api_keys` can bind a user key to another member** (capped at both people's
   permissions) — impersonation-like; consider restricting to Owner or a dedicated permission.
6. **Page guards run in the shell** (client) — the data behind every page is enforced server-side
   (ui-reads `perm`, services, RLS), so a bypass shows an empty page, not data.
7. **Email templates delete** is gated on `workflows.edit` on every surface (consistent, kept);
   **audit log** reads differ (REST `settings.view`, MCP `team.change_roles`) — align if wanted.
8. **Seven stale MCP authz entries** (tools that no longer exist) are harmless; prune later.
9. The RLS semantics fixture has no role-holding callers; `governance-rls-db` covers Viewer /
   Member / Admin / other-workspace Admin explicitly instead.
